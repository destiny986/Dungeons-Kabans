# Dungeons & Kabans

Русскоязычный дневник игры для одного мастера и небольшой группы игроков:
персонажи, предметы, действия и заклинания, события и приватная переписка.
Значения характеристик вводит мастер; приложение не рассчитывает правила D&D.

Python 3.12 · Django 5.2 LTS · SQLite · HTML/HTMX · GridStack.
Клиентские библиотеки включены в репозиторий, внешние CDN при работе не нужны.

Постоянная рабочая папка проекта — `C:\dev\Dungeons-Kabans`.
Все последующие изменения и результаты сохраняются в ней; правило закреплено в
[AGENTS.md](AGENTS.md).

## Локальный запуск в Windows

Нужен установленный Python 3.12. В PowerShell из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py serve_game
```

Окружение и зависимости устанавливаются один раз; затем достаточно команды
`serve_game`. Она применяет миграции, настраивает мастера, собирает статику и
запускает сервер в текущем терминале. Остановка — Ctrl+C. Активация окружения
не требуется. Команда доступна только при `DJANGO_ENV=local` (по умолчанию).

При первом запуске в терминале команда попросит пароль мастера и подтверждение,
скрывая ввод. Пустой пароль и несовпадение завершают запуск с ошибкой.
При последующих запусках без `MASTER_PASSWORD` существующий пароль и сессии
сохраняются. Откройте http://127.0.0.1:8000/ и введите выбранный пароль мастера.

Для запуска без вопросов заранее задайте `MASTER_PASSWORD` в окружении процесса
(либо используйте уже настроенного мастера):

```powershell
.\.venv\Scripts\python.exe manage.py serve_game 127.0.0.1:8001 --noinput --noreload
```

Адрес необязателен, по умолчанию — `127.0.0.1:8000`; `--noreload` отключает
автоматический перезапуск при изменениях кода. Без терминала или с `--noinput`
первый запуск без пароля завершается понятной ошибкой. Пароль не генерируется.
Непустой `MASTER_PASSWORD` задаёт пароль через ту же логику, что и
`bootstrap_master`: одинаковый пароль сохраняет хеш и сессии, новый отключает
прежний доступ мастера при следующем запросе, сохраняя доступы к персонажам.

Переменные из .env.example служат справочником: Django сам не читает .env.
Для локального запуска задавайте нужные переменные в окружении процесса.
Локальный сервер по умолчанию привязан к вашему компьютеру. Для игры с
других устройств нужен доступный им адрес и соответствующие ALLOWED_HOSTS /
PUBLIC_BASE_URL; производственная конфигурация описана отдельно.

## Первые шаги

1. В настройках мастера создайте предметы, действия/заклинания и события.
2. В управлении персонажами заполните лист персонажа и назначьте его содержимое.
3. Откройте приглашение и передайте игроку ссылку или QR-код.
4. Игрок сразу попадёт на страницу своего персонажа. Ссылка многоразовая до отзыва.
5. В одном браузере можно одновременно иметь доступ мастера и нескольких
   персонажей; выбор доступен через «Вернуться в игру» на главной странице.

Мастер видит общий поток чата. Игрок видит свою переписку с мастером,
полученные события и системные сообщения о своём персонаже.
Открытые страницы обновляются каждые пять секунд.

Заклинание расходует одну ячейку нужного уровня. Если таких ячеек нет,
приложение предлагает ближайший доступный более высокий уровень и ждёт
подтверждения. Закрытие окна ничего не расходует. Урон и эффекты не пересчитываются.
Поддерживаются уровни ячеек 1–7, ярость и перевоплощение друида.

## Хранение и перенос

По умолчанию SQLite находится в data/db.sqlite3, изображения — в data/media,
временные импорты — в data/imports. Эти каталоги и секреты исключены из Git.
Пути переопределяются DATA_DIR, MEDIA_ROOT и IMPORT_ROOT.

На странице управления данными мастер вручную скачивает ZIP с игровыми
записями и PNG. Чат, пароль, приглашения и браузерные сессии в ZIP не входят.
Импорт сначала проверяет архив и показывает конфликты, затем сохраняет
выбранные записи одной транзакцией. Отмена и ошибка удаляют временный архив
и подготовленные файлы, сохраняя используемые изображения.

Формат: [docs/archive-format.md](docs/archive-format.md).
Служебная очистка брошенных импортов:

```powershell
.\.venv\Scripts\python.exe manage.py cleanup_imports
```

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
node --check game/static/game/app.js
node tests/import_bulk.test.cjs
```

Тесты используют отдельную базу и временные каталоги изображений.
Проверка конкурентного списания использует настоящую файловую SQLite.
Для проверок JavaScript нужен Node.js в PATH; запуск приложения и образ Docker
его не требуют. CI выполняет эти команды после проверок Python и явно сообщает,
если Node.js недоступен.

## Доставка

[Инструкция по Docker, nginx и GitHub Actions](docs/deployment.md).
Ветка release запускает доставку на подготовленный сервер; остальные ветки
проверяются без деплоя. Данные хранятся вне образа контейнера.
Автоматических резервных копий и отката нет. Возврат к прежнему коду через
release требует сохранения совместимости миграций.

В рамках разработки производственный сервер не изменяется, release не отправляется.
Согласованные требования и план находятся в docs/superpowers.
