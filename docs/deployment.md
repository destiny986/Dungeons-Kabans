# Deployment

The release branch is the only deployment trigger. Pull requests and all pushes run
Python 3.12 tests, Django checks, a migration drift check and a separate Docker smoke
test. After both jobs pass, a push to `release` builds and pushes
`DOCKER_USERNAME/dungeons-kabans:<40-character-commit-SHA>`, stages configuration over
verified SSH, migrates once, bootstraps the master once, starts Gunicorn and checks
health. Deployment jobs share a concurrency group with `cancel-in-progress: false`;
the host also uses `flock`. GitHub can supersede a pending release with a newer
pending release, but never cancels an already running release.

No deployment has been run as part of authoring these files. Server addresses and
ports below are the previously recorded inventory, not a new live verification.

## Host setup (operator, once)

Ubuntu 22.04 needs Docker Engine, Compose >=2.30 (`env_file.format: raw`), nginx,
Python 3, curl, util-linux/flock and sudo. Recorded versions were Docker 29 and
Compose 2.40.3. Allow incoming TCP 9443 in the host/provider firewall. Keep TCP 443,
80 and 8443, Hantise on 127.0.0.1:18080 and Amnezia unchanged. Our app binds only
127.0.0.1:18081 and uses its own Compose project `dungeons-kabans`.

Prepare the private directories using the chosen deployment account in place of
`DEPLOY_USER`. That account must be able to stage in `incoming` and run the reviewed
release script with `sudo -n`; it is a trusted administrator, since deployment code
runs as root. Restrict repository/environment access accordingly.

```bash
sudo install -d -m 755 /srv/dungeons-kabans
sudo install -d -m 700 /srv/dungeons-kabans/config
sudo install -d -m 700 -o DEPLOY_USER -g DEPLOY_USER /srv/dungeons-kabans/incoming
sudo install -d -m 700 -o 10001 -g 10001 /srv/dungeons-kabans/data /srv/dungeons-kabans/imports
sudo install -d -m 755 -o 10001 -g 10001 /srv/dungeons-kabans/media
sudo nginx -t
```

Retain the existing IP SAN certificate at
`/etc/letsencrypt/live/185.232.205.216/{fullchain,privkey}.pem`, its renewal timer and
the existing successful-renewal nginx reload hook. Do not change ACME challenge
routing or existing vhosts. The new vhost listens solely on 9443. First release
stages its symlink, runs `nginx -t`, and removes that candidate if validation fails;
it reloads only a valid nginx configuration. Subsequent releases require the
installed dedicated vhost to match the reviewed file; changed nginx content needs
an explicit operator install and `nginx -t` before reload.

## GitHub and DockerHub

Create DockerHub repository `DOCKER_USERNAME/dungeons-kabans`. Use a repository
scoped credential with only pull/push and no delete permission where supported;
otherwise use the narrowest DockerHub read/write token available. Prefer enforced
immutable commit tags in the registry. Never reuse a SHA tag for different bytes.
With tag immutability enabled, a rerun that attempts to push the same tag can fail;
inspect the existing image rather than replacing it. Record the pushed image digest
from the Docker push output for an additional provenance reference. No `latest`
tag is used.

Configure the GitHub `production` environment and protect the `release` branch.
Required Actions secrets:

| Secret | Value |
|---|---|
| DOCKER_USERNAME | DockerHub namespace; lowercase user name |
| DOCKER_PASSWORD | Scoped registry token |
| HOST | `185.232.205.216` (the dispatcher rejects other destinations) |
| SSH_USER | Trusted deployment account |
| SSH_PASSWORD | That account's SSH password |
| SSH_HOST_FINGERPRINT | Independently trusted ED25519 `SHA256:...` fingerprint |
| DJANGO_SECRET_KEY | Long random production secret, at least 50 characters |
| MASTER_PASSWORD | Strong master password |

Obtain the host fingerprint from a trusted provider console or another independent
channel, for example `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256` on
the console. A value merely observed during network reconnaissance is insufficient.
The runner compares `ssh-keyscan` output against this trusted fingerprint, then uses
strict known-host checking for SSH and SCP. The SSH password is supplied through
`SSHPASS`, not an argument; other secrets are private JSON on SSH stdin. Do not add
shell tracing or print environment/config contents. Secret values with quotes,
backslashes, dollar signs and hash signs are supported literally; newline, CR, NUL
and empty values are rejected. Registry configuration uses an isolated temporary
`DOCKER_CONFIG` on both machines; root's existing Docker login is untouched.

Runtime files are root-readable mode 0600 in private configuration directories;
staging directories are 0700. Compose raw env files are never sourced as shell
scripts. `DJANGO_ENV=production`, `DJANGO_DEBUG=False`, the exact allowed hosts/CSRF
origin and public URL are generated by `deploy/runtime_config.py`. Gunicorn runs as
UID/GID 10001, two workers/two threads, with a read-only root filesystem and writable
`/data`, `/media`, `/imports`, `/tmp`. Static assets are collected while building and
served by WhiteNoise. Persisted PNGs need 0644 permissions and the media directory
0755 for nginx's worker to read them; media URLs remain protected by the internal
`/_protected_media/` nginx location. There is no public media alias.

Gunicorn access entries go to `/dev/null`, and this vhost explicitly sets
`access_log off` so the host's inherited access log cannot record reusable
`/join/<token>/` invitation URLs. Request paths, query strings and Referer values
are omitted from both access streams for successful and unsuccessful requests.
Application/Gunicorn error logging and ordinary nginx error logging remain
available. The `/join/` nginx location alone suppresses upstream-error messages,
which otherwise embed the original invitation URI. Central Django request and
development-server handlers redact `/join/<token>` after message interpolation;
their formatter also redacts such paths in exception text while preserving
tracebacks and statuses. Requests and routes remain unchanged. Review error logs
before sharing them, as other diagnostic context can still contain user data.
Do not re-enable default access logging without credential redaction. When upgrading
an earlier dedicated site, the operator must install the reviewed nginx change and
validate/reload it before considering production logging safe; the release script
deliberately refuses an unexpected site-content change.

## Local Docker bootstrap

To exercise the exact image without a server or production data:

```bash
docker build -t dungeons-kabans:local .
bash deploy/docker-smoke.sh dungeons-kabans:local
```

The smoke test creates named temporary volumes, gives them UID 10001 ownership,
runs migrations/bootstrap and production checks, then starts Gunicorn and verifies
DB-backed health. It removes only its own test container/volumes afterward. It uses
public test credentials and is separate from any deployed container. It also starts
an isolated nginx test proxy with a disposable self-signed certificate and sends a
real valid invitation, an invalid invitation and a health request with known URI,
query and Referer markers. It inspects both container log outputs without printing
the credentials or potentially unsafe logs. It then stops only the temporary app
and verifies that an invitation request producing an nginx upstream 502 also
leaves no credential marker in proxy logs. CI's self-signed TLS bypass is confined
to that test proxy; release health checks still require valid production TLS.
For ongoing
local development use the project's local Django setup; production Compose paths
refer deliberately to the prepared host directories, not your working directory.

## Release and diagnostics

A first push to `release` performs the steps above. This documentation does not
authorize a push or a server connection. The release runs migrations and
`bootstrap_master` before replacing the application container; the bootstrap
command changes the fixed master's password only when the configured password
changes. Container startup never runs migrations. During migration the previous
Gunicorn instance can still be serving traffic, so migrations must be additive and
backwards compatible. SQLite schema operations can briefly block concurrent writes.

After starting the candidate, the host checks loopback health, nginx syntax and
HTTPS health on 9443. The GitHub runner also checks HTTPS health from outside the
server, verifying the certificate without `-k`. A health or migration failure fails
the workflow; it never restores a database, restarts an earlier image or attempts
an automatic rollback. A failed health check may leave the new container running
for diagnosis, and a failed post-migration phase may leave the schema updated.

The most recently successful configuration is `/srv/dungeons-kabans/config/current`.
If a release failed, use its SHA under `config/releases/<SHA>` to inspect that
candidate instead. Run as root for these diagnostics, without printing env files:

```bash
cd /srv/dungeons-kabans/config/current
sudo docker compose --project-name dungeons-kabans --env-file image.env -f compose.production.yaml ps
sudo docker compose --project-name dungeons-kabans --env-file image.env -f compose.production.yaml logs --tail 100 app
sudo nginx -t
curl --fail https://185.232.205.216:9443/healthz/
sudo docker compose --project-name dungeons-kabans --env-file image.env -f compose.production.yaml run --rm --no-deps app python manage.py cleanup_imports
```

Install the supplied systemd service/timer after the first healthy release, from
the reviewed checkout on the host. The timer runs hourly (up to five minutes of
jitter), including one catch-up after downtime. Each run removes abandoned imports
older than 24 hours while retaining active/referenced files; the cutoff is 24 hours,
not one hour. The shared release lock prevents overlap with a migration. The service
uses the latest healthy configuration via `config/current` and does not pull an
image, migrate, back up or restart the application.

```bash
sudo install -m 644 deploy/dungeons-kabans-cleanup.service /etc/systemd/system/dungeons-kabans-cleanup.service
sudo install -m 644 deploy/dungeons-kabans-cleanup.timer /etc/systemd/system/dungeons-kabans-cleanup.timer
sudo systemd-analyze verify /etc/systemd/system/dungeons-kabans-cleanup.service /etc/systemd/system/dungeons-kabans-cleanup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now dungeons-kabans-cleanup.timer
sudo systemctl list-timers dungeons-kabans-cleanup.timer
sudo journalctl -u dungeons-kabans-cleanup.service --since today
```

These are operator setup instructions; authoring the files does not install or start
anything on the server. Run `sudo systemctl start dungeons-kabans-cleanup.service`
for a deliberate immediate cleanup. Review application logs for sensitive user
content before sharing them.
Never use `docker compose down -v`, delete/reinitialize SQLite, or prune persistent
directories to troubleshoot. No automatic backups or backup rotation are installed.
Domain ZIP export/import is a manual transfer of domain data, not a full chat,
session, invitation or operational database backup. Manual deployment of an earlier
image requires an explicit schema compatibility assessment; an earlier image may
not work after destructive migrations.

Update pins deliberately after reviewing upstream changes. The Python base image
tracks the 3.12 Debian bookworm patch line; rebuilding it can produce a different
digest, so rely on the published SHA-tagged artifact and record its digest for an
actual release. Nothing in this setup automatically updates the running container.
