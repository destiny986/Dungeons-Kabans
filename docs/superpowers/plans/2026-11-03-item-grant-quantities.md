# План: количество предметов при выдаче

**Цель:** отдельное количество каждому выбранному получателю предмета.

**Дизайн:** [согласованное поведение](../specs/2026-11-03-item-grant-quantities-design.md).

**Архитектура:** существующий Django POST вызывает атомарный `grant_catalog`;
персональные сообщения используют `ChatMessage.metadata.quantity`. Новые
зависимости и миграции не нужны. Рабочая папка — `C:\dev\Dungeons-Kabans`.

1. Добавить регрессионные тесты сервиса: разные количества, некорректные числа,
   переполнение, полный откат, повтор UUID и совместимость старых отпечатков.
   Запустить тесты до реализации и подтвердить ожидаемые падения.
2. Расширить `grant_catalog(..., *, quantities=None)` словарём UUID → количество.
   Проверять числа в сервисе, учитывать количества в отпечатке только при
   отклонении от единиц. Обновлять инвентарь и ревизии атомарно. Создавать по
   сообщению каждому получателю в порядке UUID; `message_id` — первая запись.
3. Добавить `quantity_<UUID>` в форму и извлечение выбранных значений в HTTP.
   Отсутствие поля означает 1, пустая строка — ошибка. Возвращать связанную
   форму при ошибке через HTMX и обычную страницу, сохраняя UUID.
4. Добавить синхронизацию доступности полей с обычным/массовым выбором и
   адаптивную двухколоночную строку. Показать количество в обоих чатах,
   сохранив отображение старых сообщений.
5. Проверить в браузере ширины 1440 и 390: выбор, сворачивание, polling,
   ошибки, UUID, отправку и отсутствие перекрытия длинных имён. Проверить
   обычный POST без JavaScript, права и приватность существующими тестами.
6. Обновить контракты. Выполнить полный pytest, Django check, проверку
   отсутствия миграций, node --check, import_bulk.test.cjs и git diff --check.
   Провести отдельное ревью изменений, исправить существенные замечания.

При реализации сохранять текущие незакоммиченные изменения, не создавать
worktree и не выполнять публикацию.
